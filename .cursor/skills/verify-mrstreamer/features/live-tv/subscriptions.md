# Source removal and provider admission

Source removal stops admitting work, optionally erases viewing, then deletes hidden spare logins before the main login. An erase or login-deletion refusal restores source/cache usability before teardown; an already successful optional erasure stays committed. Missing main login is the durable commit. After it, Library, catalogue-worker, Guide and Settings settle admitted writes before folder deletion, including cancellation and newer-login replacement. An interrupted refresh that never reached its first scheduler turn is cleared only after settlement and only if it is still the same owner. Cleanup failures are logged individually and removal continues without restoring the source or interrupting sibling writers. `source-removal.test.ts` holds real filesystem boundaries for original/added catalogue writes, competing refreshes, native deletion cancellation, login refusal and a queued Settings write with a remaining Live-only M3U. `roster.test.ts` retains viewing-erase refusal and the held Guide boundary; `guide-source.test.ts` covers concurrent removals. Main viewing reads recheck the saved owners after catalogue lookups. Renderer viewing reads and favourite/reorder replies use the ordered saved ids already in the subscriptions query; source changes re-read and obsolete replies cannot restore removed membership, while lower/equal sequences and newer event reads still work. The viewing-query/source-transition and favourite-order tests cover these public paths. Built-app proof must show original and added source removal, restart absence, the other source still usable, discovery fallback and favourites/reorder afterwards. Refused removal invalidates reads made during logical exclusion, including first reads still unfinished at refusal: after settlement they become stale again, so the restored source reappears without restart. Filesystem failure and cancellation injection remain service-contract evidence, separate from that UI path.

After an https stream address, `providerFetch` in `@mrstreamer/core/provider` sends no secret of the login it recognizes to http, written as is or percent-encoded as [the login on the wire](../../../../../docs/contributing/architecture.md#the-login-on-the-wire) says, in a redirect or in any address the stream's playlists name: variants, renditions, segments, keys and maps, through direct HLS, the HLS converter, a receiver's passthrough and catch-up recordings alike. Secrets are an Xtream account's username and password and a playlist link's user info and token-named query values, however short (`ProviderLogin`). A link's other query values count only as whole parts, so a setting such as `format=hlsarchive` doesn't stop a relay's `hlsarchive_index.ts`. Playback passes the stream's own address as `Provider.request`'s `from`. A credential-free http relay, a playlist Live stream's own query token and a stream a playlist lists with http still play. An entry's headers go whole to the stream's origin; elsewhere a Referer holding the link's token goes cut to its origin. `apps/desktop/test/playlist-credentials.test.ts` drives the real proxy, converter, LAN passthrough, catch-up and title/download paths against a loopback http server that must see no request for a refused address, including a moved playlist's relative addresses, an http playlist an https stream redirected to, the link's settings, a three-character token, a token spelled with a plus as written and its other characters escaped, a login with a space beside a path's plus, and a token beside an escape that is no UTF-8. `credentials.test.ts` refuses an Xtream stream redirected to http with a three-character password joined to other text. `packages/core/test/provider.test.ts` holds the matching rules: combined, re-encoded, joined, key-only, header, multihop and uncertain values, an Xtream account's short login, and a password as each part of an address spells it. The loopback and LAN proxies answer an unreadable request target such as `http://[` with 400 and leave no unhandled rejection (`receiver.test.ts`). The fake provider and playlist serve plain http, so the baseline scenarios prove only the unchanged http paths; an https playlist in the built app needs its own check with the https hosts answered at main's fetch.

Connection admission for local and receiver opens is owned by `services/playback-coordination.ts` (`PlaybackCoordination`). It counts the provider requests sessions and recordings read: a local live session and a recording of the exact same source (one channel's same stream, MPEG-TS or clear HLS, a multivariant playlist held to one variant while both read) share one capture (`playback/live-capture.ts`) and one connection, and opening Watch of a channel a recording reads joins it instead of failing with `recording-holds`. A joining Watch held to a variant its player can't decode fails as unsupported instead of loading another (`renderer/hls-startup.test.ts`), and its repaired retry never shares, so a recording holding the last connection refuses it with `recording-holds` (`recordings.test.ts`). A session's close waits for a capture it read last to end its request. Playback reports media session registration and scope closure; downloads consume its per-subscription lease and availability stream. The existing playback, downloads and output service suites cover stale turns, switching and reclaim closure. The per-title upstream reader policy remains separate.
