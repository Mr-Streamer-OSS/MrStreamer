# Local-copy progress

## Default local-copy progress

A recording's resume position follows [Default local-copy progress](../downloads/progress.md#default-local-copy-progress), with copy kind `recording`. Opening its local copy seeds Default’s legacy position; listing recordings does not. Refused progress writes remain pending in the main runtime for its next retry check, even if the player closes or schedules cannot be read. Its focused tests and candidate acceptance journey are listed there.

## Growing-copy backend checkpoint (0.0.24)

The recorder-owned file cases in `apps/desktop/test/recordings.test.ts` exercise retained wall-clock gaps, unknown final indexed duration, and an exact open session settling to the file's final sample end. The existing file-session probe is reused when already settled; an active session coalesces one bounded, cancellable local probe after settlement, checks the same revision and incarnation, and retains a failed attempt as refusal until reopened. Unchanged track indexes remain the indexes used by the transcoder. A changed inspected track layout refuses that session rather than publishing stale track indexes. The index's presentation span is main-only and is never a final-sample claim.

A run from a nonzero position starts at the last verified H.264 IDR at or before it. The recording index keeps each IDR whose access unit carries SPS and PPS and whose PAT and PMT come just before it, with no other picture between; ffmpeg reads the recorded bytes from that PAT on standard input through the session's own follow reader, maps tracks by transport PID, and the run fails unless its first copied picture is that IDR. x-start stays the first copied packet minus the origin the session's ffprobe reported. `playback.copyState` reports the same range in `recording.seekable`, also after the recording ends. An interrupted recording, a selected subtitle, a converted or reordered picture, a track whose PID ffprobe and the recorded tables do not share, a missing reported origin, or a position outside that range still returns 416. Byte offsets and PIDs stay in main.

`Recordings.copy` admits a recording while it records once its own index has read the recorded program, under the existing kind-and-id approval (`apps/desktop/test/profile-policy.test.ts`); one whose program cannot be read still refuses. The seek cases decode the returned picture against an independent decode of the recorded bytes, compare the chosen sound track's packets, and follow appended bytes. Subtitle alignment on such a run, HEVC and other codecs, wrapped clocks and changed-layout remapping remain unproved and refused; these backend cases do not qualify renderer integration, native output, installed builds or real-provider behavior. No renderer journey is mounted by this checkpoint.
