# Local-copy progress

## Default local-copy progress

A recording's resume position follows [Default local-copy progress](../downloads/progress.md#default-local-copy-progress), with copy kind `recording`. Opening its local copy seeds Default’s legacy position; listing recordings does not. Refused progress writes remain pending in the main runtime for its next retry check, even if the player closes or schedules cannot be read. Its focused tests and candidate acceptance journey are listed there.

## Growing-copy backend checkpoint (0.0.24)

The recorder-owned file cases in `apps/desktop/test/recordings.test.ts` exercise retained wall-clock gaps, unknown final indexed duration, and an exact open session settling to the file's final sample end. The existing file-session probe is reused when already settled; an active session coalesces one bounded, cancellable local probe after settlement, checks the same revision and incarnation, and retains a failed attempt as refusal until reopened. Unchanged track indexes remain the indexes used by the transcoder. A new program table on the same verified clock refreshes the session's tracks by identity (PID, codec, language and purpose in the tables): a kept track keeps its id, a track the last table dropped leaves the listing and its runs return 416, and a sound track a new table adds is listed under a new id once one bounded ffprobe of the file from that table's first access point describes it. A changed table the index cannot verify, such as one whose clock steps back or moves to another PID, still refuses that session rather than publishing stale track indexes. The index's presentation span is main-only and is never a final-sample claim.

A run from a nonzero position starts at the last verified H.264 IDR at or before it. The recording index keeps each IDR whose access unit carries SPS and PPS and whose PAT and PMT come just before it, with no other picture between; ffmpeg reads the recorded bytes from that PAT on standard input through the session's own follow reader, maps tracks by transport PID, and the run fails unless its first copied picture is that IDR. x-start stays the first copied packet minus the origin the session's ffprobe reported. `playback.copyState` reports where runs with every listed sound track can start in `recording.seekable`, also after the recording ends; `recording.audioSeekable` gives a track whose range differs, one a table added or dropped, and a run from 0 with an added track starts at its first access point. `recording.subtitleSeek` is false: a nonzero run with a subtitle returns 416. An interrupted recording, a converted or reordered picture, a track the recorded tables do not name, a missing reported origin, or a position outside the selected track's range also returns 416. Byte offsets and PIDs stay in main.

`Recordings.copy` admits a recording while it records once its own index has read the recorded program, under the existing kind-and-id approval (`apps/desktop/test/profile-policy.test.ts`); one whose program cannot be read still refuses. The seek cases decode the returned picture against an independent decode of the recorded bytes, compare the chosen sound track's packets, and follow appended bytes; the table-change case rearranges PIDs so that index mapping would return the other track's packets. Subtitle alignment on such a run, subtitle tracks a new table adds, HEVC and other codecs, and wrapped clocks remain unproved and refused; these backend cases do not qualify renderer integration, native output, installed builds or real-provider behavior. No renderer journey is mounted by this checkpoint.
