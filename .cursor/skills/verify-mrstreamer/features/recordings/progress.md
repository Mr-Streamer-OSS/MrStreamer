# Local-copy progress

## Default local-copy progress

A recording's resume position follows [Default local-copy progress](../downloads/progress.md#default-local-copy-progress), with copy kind `recording`. Opening its local copy seeds Default’s legacy position; listing recordings does not. Refused progress writes remain pending in the main runtime for its next retry check, even if the player closes or schedules cannot be read. Its focused tests and candidate acceptance journey are listed there.

## Growing-copy backend checkpoint (0.0.24)

The recorder-owned file cases in `apps/desktop/test/recordings.test.ts` exercise retained wall-clock gaps, unknown final indexed duration, and an exact open session settling to the file's final sample end. The existing file-session probe is reused when already settled; an active session coalesces one bounded, cancellable local probe after settlement, checks the same revision and incarnation, and retains a failed attempt as refusal until reopened. Unchanged track indexes remain the indexes used by the transcoder. A new program table on the same verified clock refreshes the session's tracks by identity (PID, codec, language and purpose in the tables): a kept track keeps its id, a track the last table dropped leaves the listing and its runs return 416, and a sound track a new table adds is listed under a new id once one bounded ffprobe of the file from that table's first access point describes it. A changed table the index cannot verify, such as one whose clock steps back or moves to another PID, still refuses that session rather than publishing stale track indexes. The index's presentation span is main-only and is never a final-sample claim.

A run from a nonzero position starts at the last verified H.264 IDR at or before it. The recording index keeps each IDR whose access unit carries SPS and PPS and whose PAT and PMT come just before it, with no other picture between; ffmpeg reads the recorded bytes from that PAT on standard input through the session's own follow reader, maps tracks by transport PID, and the run fails unless its first copied picture is that IDR. x-start stays the first copied packet minus the origin the session's ffprobe reported. `playback.copyState` reports where runs with every listed sound track can start in `recording.seekable`, also after the recording ends; `recording.audioSeekable` gives a track whose range differs, one a table added or dropped, and a run from 0 with an added track starts at its first access point. `recording.subtitleSeek` is false: a nonzero run with a subtitle returns 416. Subtitle tracks follow the last verified table as sound tracks do, each identified by every page its table lists under its PID, so a PID that carries another language after a new table is a new track. One a new table adds is listed once the table's one bounded probe describes it, and only when that table took over at an access point; a run from 0 with it starts there and maps it by PID. A failed probe of a new table fails `copyState` and runs, and the next request probes again. The subtitle feed (`only=subtitles`) offers the same tracks as runs: one no longer listed returns 410. An interrupted recording, a converted or reordered picture, a track the recorded tables do not name, a missing reported origin, or a position outside the selected track's range also returns 416. Byte offsets and PIDs stay in main.

The recorder retains one incremental index per recording across opens, releasing it on removal or shutdown; file incarnation checks use lossless device and inode strings. The reopen-after-append case verifies retained revisions and exact identity.

`Recordings.copy` admits a recording while it records once its own index has read the recorded program, under the existing kind-and-id approval (`apps/desktop/test/profile-policy.test.ts`); one whose program cannot be read still refuses. The seek cases decode the returned picture against an independent decode of the recorded bytes, compare the chosen sound track's packets, and follow appended bytes; the table-change case rearranges PIDs so that index mapping would return the other track's packets. The added-subtitle case decodes the feed's DVB page with the player's decoder at its recorded time and matches its packet on PID 0x103, and a table that took over one picture before its keyframe leaves the subtitle unlisted. Subtitle alignment from a nonzero position, HEVC and other codecs, and wrapped clocks remain unproved and refused; these backend cases do not qualify native output, installed builds or real-provider behavior.

## Renderer (0.0.24)

The title player (`apps/desktop/src/renderer/src/player/title-player.ts`) keeps an open recording's `RecordingSessionState` from its `playback.openCopy` answer, or one `playback.copyState` read when that answer has none yet, and reads it again on `playback.copyChanged` for the same session, one read at a time; a failed read keeps the last facts. Track lists follow it by id, a chosen subtitle the session drops leaves the screen, and a dropped sound falls back for the next run. Every run of a recording starts at 0 or inside the chosen tracks' ranges (`recordingRanges`: the sound's `audioSeekable` entry, else `seekable`, none with a subtitle while `subtitleSeek` is false), else at the nearest such point. While it grows, `duration` is the span observed so far: the bar reads "{time} so far" with a red dot at its end while it records, Go to latest seeks to the last range's end and is disabled within 10 s of it, and progress saves against that verified reach, never as watched; with no length and no range the player shows the clock and Length not known. A place counts as in the credits only when saved against the final verified length. An ended session without a verified length saves its position with duration 0 (unknown), which never means watched. Version 0.0.23 cannot reopen a recording after a 0.0.24 session saves an unknown-length checkpoint; downgrade compatibility is not qualified. UI copy-change notifications coalesce appends over one second, with status, gap and final changes sent immediately; byte-reader wakeups remain per write. Wall-clock `gaps` are never drawn on the player bar. The view is the declared hunk in `apps/desktop/src/renderer/src/features/titles/TitleWatch.tsx`. The `recordings` scenario in [desktop](desktop.md) drives it; focused renderer tests in `recordings-standalone.test.ts` cover watched-ended replay, growing-checkpoint resume, active-only failed-place retry and unknown-final progress. These checks do not establish rendered player edge-state layouts.
