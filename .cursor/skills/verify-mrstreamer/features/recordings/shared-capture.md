# Shared capture

Shared capture (`main/playback/live-capture.ts`, `live-history.ts`, `hls-capture.ts`): a live source is shared only when the subscription, its login revision, the channel's own id (as the library lists it, never another of its streams' ids), the stream's id, its format, the address and the headers all match, so two channels of a playlist at one address each take a connection. An HLS stream is shared only when its playlist names clear MPEG-TS segments itself, as `hls-ts-input.ts`'s reader takes them: Watch stays on hls.js and the proxy, the recording on that reader, and both ask through `LiveCaptures.resource`, which asks the provider once for a playlist read again within half its target duration (the latest answer standing at the address asked, the address it redirected to and any that redirected there, older tokens' entries dropped) and once for each segment, known by its media and discontinuity sequence numbers and its address without the query (the addresses the last three playlist reads named, all forgotten with every kept segment when the media sequence goes back, as after a packager restarted), so a query token still shares and another host or path doesn't, read from the provider as fast as its fastest reader reads; the provider's own playlist text and segment bytes reach both, discontinuities included. The first playlist answer decides sharing, an empty or non-playlist answer deciding nothing; a later one that is no longer clear media is passed on but not kept, and the HLS reader stops at it. The last 4 segments to complete, 64 MiB at most, stay in memory for a reader still to come; a reader further behind asks the provider again, one segment nobody reads any more while it arrives is aborted, a reader is never given the same playlist answer twice, an owner asking for another stream leaves the one it read, and the last owner leaving waits for every request to close. A multivariant playlist is shared too: the first answered is kept and given to each owner as its multivariant playlist, each media playlist keeps its own read count and numbering, and while two or more owners read, all hold the variant the first of them read (Watch's when a recording joins, the recording's when Watch joins), a request for another variant's playlist being answered with the held one's. `LiveCaptures.fixed` names the held variant, Playback tells the player through `playback.fixed` with the proxy address hls.js knows it at, the renderer engine holds that level (`loadLevel`) and shows it in the Recording popover, and once one owner is left the hold ends and the player is told null, back to Auto. A variant is known by its address as the kept playlist names it, query included, else the most specific whose query the address has with a player's added delivery directives, else by its path when only one variant has it; its playlist's redirect target and the addresses a multivariant playlist asked for again names it by (same place, same path) are aliases, while the variants held stay the first's. Segments are known within their playlist, so two variants' segments never meet. Only a variant the HLS reader records and that has no subtitle rendition of its own (which a recording would leave out) is held: `reading` and `joins` count such a stream only while the variant a joiner would hold is one. A reader admitted to share it (`resource`'s `joining`: a recording that found `reading`, Watch opened `joining` a recording) joins, and a race with Watch's quality then holds the variant it reads; any other reader coming while the others read an unholdable variant asks the provider itself for as long as it reads, on the connection it was admitted on. A byte-range request and HLS Watch that converts are never shared. Each capture keeps the provider's bytes in pieces of 188 × 22,000 bytes; a full piece every reader has read goes at once, and one a reader still needs is written to the data folder's `live-history/`, emptied as the app starts, so readers at the live edge write nothing; all captures together keep at most 2 GiB (`TEMPORARY_BYTES`) and never write below 5 GB free. One writer takes every capture's full pieces in turn, so the budget holds across captures. The oldest piece goes first, also while a reader is paused on it, and its file is removed before the next is written; a file the system won't remove still counts against the budget and stops that capture's writes. At most two full pieces wait in memory for the disk, and a disk that refuses a write keeps memory only, so the live edge still plays; a reader paused longer than those pieces last then falls behind. A reader whose bytes were evicted fails with `FellBehind`: a recording reads that as cut by the disk and goes on after the gap; others read on. A provider that sends nothing for 15 seconds ends the capture and every reader, and the next request opens a fresh one, as a recording's own watchdog would. The last reader leaving aborts the provider request and removes the files before its connection counts free (`LiveCaptures.idle`). `apps/desktop/test/playback.test.ts` "live captures" and "live history" prove one request per exact source, another login revision, channel or stream at the same address opening its own, an HLS media playlist and each segment asked once for two readers, an empty first answer deciding nothing, only the last four segments kept, the playlist the same at a redirect's both addresses and its segments under a token the same segments, and an abandoned segment's close awaited by the last owner leaving, a reader left alone reading the playlist anew, an owner moving to the channel's next stream no longer counting as reading the first, a segment never answered from before the numbering went back, every reader of a multivariant HLS playlist held to the variant read first until one is left, a variant it can't record shared with nothing, two captures' files within one budget together, nothing written while every reader keeps up, a silent provider ending every reader and the next request asking anew, a request abandoned while it opens ending before `idle` settles, a reader joining on a packet boundary, the files within the budget while one reader reads nothing, only that reader failing, memory-only reading with an unwritable folder, and pictures decoded from a piece found by time (`offsetAt`). Rewind, multiview and receiver sharing are not part of it, nor rewinding HLS: its kept segments are not a history.
