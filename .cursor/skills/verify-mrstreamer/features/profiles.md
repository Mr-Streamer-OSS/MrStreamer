# Viewing profiles

## Sub-features

The Default profile. An installation's existing personal state (viewing record, Watchlist, custom channel lists, `preferences.json`) is Default's in place; binding it moves, copies and rewrites nothing. The older import of favourites and recent channels from a pre-viewing-record `preferences.json` still runs as before. Subscriptions, guides, downloads and recordings stay installation-owned. No second profile, switcher or profile control is exposed until personal state, including local-copy progress, is fully profile-scoped. See the [user guide](../../../../docs/user/profiles.md).

## How to get to it (user POV)

Nothing new is visible. An upgraded installation shows the same favourites and their order, recent channels, Continue watching and progress, Watchlist, custom lists and Settings values as before, and again after a restart. Going back to the previous release still reads them.

## Public seam

`profiles.active` (main `handlers/profiles.ts`) answers Default with the registry's revision, `{ id: "default", revision: 1 }` when this release wrote it. The registry lives in `mrstreamer.db` (`platform/profile-store.ts`): the first start writes it in one transaction, never replaces rows already there, and older builds never read it. Until the registry has been read once, a locked or unwritable database fails the call rather than guess a profile, and a later call or start retries; after that the profile is answered from memory for the runtime's life. A database that can't open fails every call until a restart. A registry a later release left with another profile active fails the call and is left unchanged, because this release shows Default's viewing alone. The existing legacy `preferences.json` list import keeps its own import marker.

## Verification

`apps/desktop/test/profiles.test.ts` covers, through the services the IPC handlers call: personal state saved by a build without the registry reads back identically after the upgraded start and a restart, with Default at revision 1; and a start while another connection holds the write lock answers no profile, then Default once the lock is released, with the legacy favourites imported after the refused start and not again when the lists reappear in the file; and a registry naming another active profile fails the call across restarts.

For built-app proof, run the baselines whose state Default keeps (`live-tv`, `watchlist`, `custom-lists`, `preferences`) and a round trip through the prior release's packaged executable on one owned profile, as `custom-lists-round-trip <executable>` does for lists: save state in the prior release, start this build, restart it, and start the prior release again. Linux evidence is not macOS or Windows installed-upgrade acceptance; those need the [installed upgrade](../../../../docs/contributing/testing.md#installed-upgrade) run of a published candidate.

## Backend isolation seam

`apps/desktop/src/main/services/profiles.ts` also provides `ProfileSessions` for backend integration. It is not exposed by the window's IPC handlers. Each admitted operation retains its owner and personal store context across a switch. Default keeps its existing database and preferences paths; other owners use separate personal databases and preference files. Names and file paths never determine ownership of a provider's IDs or command receipts. Profile Settings overlay consent from the installation's Analytics owner rather than save a second consent choice.

Switching requires an explicit interactive-cleanup callback; an owner without that callback or the installation consent dependency cannot become active through this module. Deletion refuses Default and the active owner, tombstones another owner, waits for admitted operations and closes its handle before removing its personal directory. A failed close preserves the tombstone and directory; that handle stays closed and a restart can retry disposal. A failed recursive directory removal can leave a partly removed personal directory with its tombstone; retry resumes removal. A failed final registry write leaves the tombstone pending after directory removal. These failure orderings have not been induced on native platforms. Household media and job files are outside that directory. Source erasure visits every registered owner and invalidates earlier admissions. Separate databases cannot commit together: an owner erased before another fails stays erased, the call fails, and retry visits every owner again. Subscription removal awaits this erasure before claiming success. Partial erasure restores the subscription for retry but never restores invalidated admissions or personal records already erased.

The public module tests in `apps/desktop/test/profiles.test.ts` exercise identical source, content, list and command IDs; retained admissions; personal preferences across restarts; installation consent through the real Analytics owner; cross-database erasure failure and retry; and inactive-profile deletion with household data retained. Copy-open paths capture a `profile-copy-progress.ts` admission before file checks. Copy progress writes and recording retries retain that owner, including when the active viewer changes. The public tests also cover a held catalogue read across worker reconfiguration, recoverable configuration refusal, stale desktop requests after switching away and back, and interactive playback closing while a household recording keeps its ID and stream. Default retains its existing malformed-file compatibility; new private preference files refuse malformed or schema-invalid reads without saving defaults over the file.

Desktop transport carries an immutable owner and revision outside the unchanged domain inputs. Unowned bootstrap calls address only Default revision 1. Personal events carry their originating revision; queued events never acquire the viewer active when they are delivered. `apps/desktop/test/renderer/profiles.test.ts` exercises late requests, settled replies, preferences/download/output events, away/back revisions, language read/save continuations, a visible switch-language reload failure and retry, and lifecycle mutation payloads through the production renderer modules. Test support unwraps transport and supplies scripted replies; it does not enforce admission or infer event owners.

Receiver tests use a fake external adapter with delayed picker replies and a held completion around a real viewing-record checkpoint. Old success/refusal, media failure, release, loss and stopped callbacks preserve replacement sessions, including a replacement on the same connection and profile. Current callbacks still save and publish their outcomes. Broken-guard controls fail the protected public assertions. These are source/service tests, not hardware receiver, native close-failure, installed-upgrade or real-provider claims. Lifecycle IPC remains explicitly gated: `apps/desktop/src/main/index.ts` composes `profileHandlers({ profiles })`, so list, create, switch and remove refuse.

## Profile menu (built, not mounted)

`apps/desktop/src/renderer/src/features/profiles/ProfileMenu.tsx` is Paper A's avatar menu: every profile with the active one checked, switching from a row, Delete with a question first for an inactive non-Default profile, New profile with a name field (Escape leaves the field, not the menu), and a translated household-sharing footnote. A refused list read or change shows its error with Retry; a refused deletion closes its question and the list shows the profile as deleting with its own Retry, since main keeps the tombstone. A failed reload after a switch shows on the window with Retry, which starts profile sync again (`apps/desktop/src/renderer/src/app/App.tsx`). Nothing mounts the menu while the gate is off. Exposure adds it to `apps/desktop/src/renderer/src/components/WindowBar.tsx` beside Settings in the same change that passes `sessions` and `enabled` to `profileHandlers`.

`apps/desktop/test/renderer/profiles.test.ts` drives the menu through its controls: create with a trimmed name, a held then refused deletion that stays listed with Retry until it succeeds, and a held then refused switch in Dutch whose Retry completes the switch. The assembled two-profile journey in the built app, keyboard focus order and the remaining evidence wait for exposure.
