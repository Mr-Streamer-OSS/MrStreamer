# Viewing profiles

## Sub-features

The Default profile. An installation's existing personal state (viewing record, Watchlist, custom channel lists, `preferences.json`) is Default's in place; binding it moves, copies and rewrites nothing. The older import of favourites and recent channels from a pre-viewing-record `preferences.json` still runs as before. Subscriptions, guides, downloads and recordings stay installation-owned. Named profiles, switching and inactive-profile deletion use the avatar beside Settings. Independent source review and public isolation controls precede enablement; assembled app evidence has its separate limits below. See the [user guide](../../../../docs/user/profiles.md).

## How to get to it (user POV)

Use the profile avatar in the window bar to create a profile, switch viewers or delete an inactive profile. During a recovery error it remains available beside the brand and Retry, while unavailable navigation stays hidden. An upgraded installation shows the same favourites and their order, recent channels, Continue watching and progress, Watchlist, custom lists and Settings values as before, and again after a restart. Switch to Default before returning to a single-profile release; a build that recognizes only Default refuses personal-copy progress while a named profile is selected.

## Public seam

`profiles.active` answers the durably selected owner and revision. The registry lives in `mrstreamer.db` (`platform/profile-store.ts`); initialization is transactional and read failures remain visible. `ProfileSessions` supplies the runtime owner, including named profiles. Lifecycle composition supplies `profiles`, `sessions: profileSessions` and `enabled: true` to `profileHandlers`. The public methods list, create, switch and remove retain their admitted-owner checks. Admission requires the exact requested owner and revision. Configuration failure leaves admission closed, while active/list remain readable for explicit recovery. Retrying the selected profile configures it without resaving obsolete playback or changing its revision; selecting another profile uses the freshly read durable owner. Ordinary switches save playback before selection.

## Verification

`apps/desktop/test/profiles.test.ts` covers, through the services the IPC handlers call: personal state saved by a build without the registry reads back identically after the upgraded start and a restart, with Default at revision 1; and a start while another connection holds the write lock answers no profile, then Default once the lock is released, with the legacy favourites imported after the refused start and not again when the lists reappear in the file; and an invalid registry entry without a usable profile name fails across restarts. Valid named profiles restore their own owner and revision.

For built-app proof, run the baselines whose state Default keeps (`live-tv`, `watchlist`, `custom-lists`, `preferences`) and a round trip through the prior release's packaged executable on one owned profile, as `custom-lists-round-trip <executable>` does for lists: save state in the prior release, start this build, restart it, and start the prior release again. Linux evidence is not macOS or Windows installed-upgrade acceptance; those need the [installed upgrade](../../../../docs/contributing/testing.md#installed-upgrade) run of a published candidate.

## Backend isolation seam

`apps/desktop/src/main/services/profiles.ts` also provides `ProfileSessions` for backend integration. The window’s lifecycle handlers compose this module after isolation review and public negative controls. Each admitted operation retains its owner and personal store context across a switch. Default keeps its existing database and preferences paths; other owners use separate personal databases and preference files. Names and file paths never determine ownership of a provider's IDs or command receipts. Profile Settings overlay consent from the installation's Analytics owner rather than save a second consent choice.

After successful catalogue configuration, the optional configured callback receives the captured owner and Settings while the lifecycle lock holds. Main reads that owner’s interface language, applies it to native text and menus and refreshes the tray. A refused callback keeps admission closed for retry. Restored-owner startup retains the resolved language until main’s bindings are ready and revalidates the original owner and revision before application. Switching requires an explicit interactive-cleanup callback; an owner without that callback or the installation consent dependency cannot become active through this module. Deletion refuses Default and the active owner, tombstones another owner, waits for admitted operations and closes its handle before removing its personal directory. A failed close preserves the tombstone and directory; that handle stays closed and a restart can retry disposal. A failed recursive directory removal can leave a partly removed personal directory with its tombstone; retry resumes removal. A failed final registry write leaves the tombstone pending after directory removal. These failure orderings have not been induced on native platforms. Household media and job files are outside that directory. Source erasure visits every registered owner and advances that source’s generation before draining operations. Admissions capture generations before asynchronous work; core viewing commands validate only their named sources, including inside the commit transaction before receipt lookup. Viewing, Watchlist and channel-list writes check the captured source generation, including existing transaction guards and member removal. Erased-source callbacks remain refused after failed removal restores a subscription, while untouched-source callbacks retain their admission. Separate databases cannot commit together: an owner erased before another fails stays erased, the call fails, and retry visits every owner again. Subscription removal awaits this erasure before claiming success. Partial erasure restores the subscription for retry but never restores erased-source callback validity or personal records already erased.

The public module tests in `apps/desktop/test/profiles.test.ts` exercise identical source, content, list and command IDs; retained admissions; personal preferences across restarts; installation consent through the real Analytics owner; cross-database erasure failure and retry; and inactive-profile deletion with household data retained. Focused public cases also cover exact-owner configuration recovery, the household-write/permit-drain cycle, source-specific retained callbacks after failed removal restores the roster, and erasure crossing a held channel read. Copy-open paths capture a `profile-copy-progress.ts` admission before file checks. Copy progress writes and recording retries retain that owner, including when the active viewer changes. The public tests also cover a held catalogue read across worker reconfiguration, recoverable configuration refusal, stale desktop requests after switching away and back, and interactive playback closing while a household recording keeps its ID and stream. Default retains its existing malformed-file compatibility; new private preference files refuse malformed or schema-invalid reads without saving defaults over the file.

Desktop transport carries an immutable owner and revision outside the unchanged domain inputs. Unowned bootstrap calls address only Default revision 1. Personal events carry their originating revision; queued events never acquire the viewer active when they are delivered. `apps/desktop/test/renderer/profiles.test.ts` exercises late requests, settled replies, preferences/download/output events, away/back revisions, language read/save continuations, a visible switch-language reload failure and retry, and lifecycle mutation payloads through the production renderer modules. Test support unwraps transport and supplies scripted replies; it does not enforce admission or infer event owners.

Receiver tests use a fake external adapter with delayed picker replies and a held completion around a real viewing-record checkpoint. Old success/refusal, media failure, release, loss and stopped callbacks preserve replacement sessions, including a replacement on the same connection and profile. Current callbacks still save and publish their outcomes. Broken-guard controls fail the protected public assertions. These are source/service tests, not hardware receiver, native close-failure, installed-upgrade or real-provider claims. Lifecycle IPC is composed in `apps/desktop/src/main/index.ts`; proof of the assembled controls remains separate from these service tests.

## Profile menu

`apps/desktop/src/renderer/src/features/profiles/ProfileMenu.tsx` is Paper A's avatar menu: every profile with the active one checked, switching from a row, Delete with a question first for an inactive non-Default profile, New profile with a name field (Escape leaves the field, not the menu), and a translated household-sharing footnote. A refused list read or change shows its error with Retry; a refused deletion closes its question and the list shows the profile as deleting with its own Retry, since main keeps the tombstone. A failed reload after a switch shows on the window with Retry, which starts profile sync again (`apps/desktop/src/renderer/src/app/App.tsx`). No page is mounted meanwhile, so the window bar keeps the brand, drag area and profile menu, without pages, Back, notices, Search or Settings. The popup scrolls within the available viewport height, and profile rows can grow with their text. The menu ends the window bar in `apps/desktop/src/renderer/src/components/WindowBar.tsx`, beside Settings in the normal window and beside the brand during recovery. With no subscription saved it ends Connect's bar (`apps/desktop/src/renderer/src/features/connect/ConnectScreen.tsx`) and the standalone Downloads and Recordings bar (`OfflineBar` in `apps/desktop/src/renderer/src/features/downloads/DownloadsPage.tsx`). Search and Settings retain their existing source-count restrictions.

`apps/desktop/test/renderer/profiles.test.ts` drives the menu through its controls: create with a trimmed name, a held then refused deletion that stays listed with Retry until it succeeds, a held then refused switch in Dutch whose Retry completes the switch, the startup error window with its profile control and Retry while unavailable navigation stays hidden, and, with no subscription saved, a switch from Connect, a switch from Downloads opened there and the control on Recordings opened there. Both Retry and an explicit switch back to Default restore navigation in the public component tests. For assembled acceptance, drive creation, switching, deletion and non-Default restart through the real controls with the same source and content IDs. Check private lists, progress, language and other preferences; recovery refusal and Retry; keyboard focus, a short viewport and enlarged text; all five translations; household downloads and recordings across switches; and source erasure across viewers. Baseline or DOM tests alone do not prove this journey. Native, installed-upgrade, real-provider and receiver acceptance require their own actual runs; do not infer them from Linux fake-provider evidence.

## Kids policy backend

The additive `profiles.policy` and `profiles.setPolicy` commands read and replace PIN-protected approvals; lifecycle commands accept an optional PIN. Policies reference inactive non-Default profiles. Online identities include subscription, kind and provider ID; household approvals distinguish download and recording IDs. Series approvals cover their episodes. Profile admission captures policy and selected revision; unreadable policy refuses admission, failed saves retain previous approvals, and changed-viewer or changed-policy replies are refused before publication. Policy edits require leaving an active kids profile first. Source management, household-file management and recording-rule/schedule management remain unavailable to kids; safe pause/stop/Quit keep their existing routes.

`apps/desktop/test/profile-policy.test.ts` exercises the real lifecycle handlers and IPC dispatch with the fake provider: wrong PIN and escape/management refusal; exact online identity and forbidden public mutations/opens; browse/history/metadata filtering; unreadable-policy refusal and repair; a held reply across an away/back switch; a hidden household recording whose stream continues and can still be safely stopped; notification suppression and closure without changing reminder receipts; mixed-version primary artwork, approved catalogue/Watchlist paging and suppression of saved fallback names; failed policy writes and restart. Broken-guard controls verify the protected public assertions fail without enforcement. The OnDemand worker builds a request-local filtered index before grouping, artwork, counts and paging, without replacing household storage or its cached index. The existing profiles tests retain Default and subtitle ownership and admission/drain protections.

The security-review cases also exercise canonical and secondary-only live approvals, no automatic fallback to an unapproved stream after the approved one fails, Home recommendations with a restricted grouped seed and candidates beyond restricted results, filtered public status counts, adult replies held across unrelated policy edits, personal removal and reminder controls, session diagnostic reads, deletion tombstones and database-open failure. Adult reminder banners survive a kids visit while system notices stay suppressed and stored delivery receipts remain intact. Startup tolerates an unavailable active-owner read so household setup continues; public admission still refuses that unreadable state. Catalogue event forwarding re-reads the status under captured admission and checks it before publication; this assembled event path and the startup window still need runtime proof.

This is backend proof. No native, installed, production or hardware-receiver acceptance follows from these service/IPC tests.

## Kids management UI

The profile menu marks kids rows _Kids · allowed titles only_ and, for an adult viewer, ends with Paper A's lock row **Manage profiles** · PIN. A change the PIN protects (leaving a kids profile for an adult, or adding or deleting once kids profiles exist) asks for the PIN in the menu first; a PIN refusal from main asks again with the field cleared and focused, and Escape cancels the change, not the menu. The PIN is passed through `apps/desktop/src/renderer/src/features/profiles/profiles.ts` with that call only and is kept out of the mutation's variables and the query cache. `ProfileManager.tsx` opens a sheet after the menu closes: it probes `profiles.policy` without a PIN, which answers only while none is set, otherwise shows the PIN prompt. Unlocked, it lists inactive non-Default profiles with a kids checkbox (the active one disabled), and for the chosen kids profile a search over the adult viewer's channels, movies and series with one row per version, the approved online sources by name, and every download and recording. Save sends the complete policy with a first or changed PIN typed twice; a refused save keeps the draft with its error for another Save, and a failed read shows Retry. `ProfileControls.tsx` holds the shared avatar, masked digits-only PIN field and failure row.

Assembled evidence on Linux with the fake provider and TMDB, driven through real pointer and key input over CDP: two named profiles, PIN set through the manager after local refusals of a missing and a mismatched PIN, one channel and one movie version approved, the kids home showing only the approved channel, wrong and then correct PIN when leaving the kids profile, PIN-protected create, the manager's PIN gate with a wrong PIN, Tab order through the sheet, a 900×520 viewport with 24 px root text, and the menu and manager in Dutch, French, German and Spanish. Alongside the menu cases above, `apps/desktop/test/renderer/profiles.test.ts` drives the manager through Cancel, Close, Escape and a successful Save, checking focus returns to the profile control. It also cancels a pending Save and reopens the manager with either an editable draft or a held policy read: the earlier Save succeeding leaves the new visit open without returning focus to the profile control, preserves its draft or loading state, and the new visit’s own Save closes it and restores focus. These happy-dom tests use a fake bridge with scripted replies; they prove renderer behavior, not backend PIN enforcement or policy persistence, built-app interaction, or native acceptance. Native, installed and real-provider runs are not claimed.

Focused Linux fake-provider proof also covers channel search showing separate FHD, HD and SD choices with source labels, saving only the HD choice, and reopening the manager with only that exact stream ID approved.
