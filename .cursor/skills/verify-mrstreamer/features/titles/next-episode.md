# Next-episode settings and acceptance

Next-episode autoplay and its exact whole-second delay are separate controls in **Settings > Playback**. The optional `nextEpisodeDelaySeconds` accepts 0 through 60, with 10 as the default and **Instant** at 0. Each ended episode snapshots its delay. Settings holds even Instant, then rechecks the final saved autoplay policy on release. Final Off or Cancel leaves manual **Next episode**, N and media-next available. An off/on edit while held resumes the saved remainder; delay edits apply to the next countdown. A failed policy read leaves manual Next. Unsupported stored delay values use 10 effectively while the raw leaf survives unrelated saves and original-source removal.

Run `xvfb-run -a pnpm verify:desktop next-episode` after building for actual media-ended paths at 0, custom 37 and 60. It selects the two-season Dutch fixture through Versions and reaches the Position range with Tab before seeking with End. It captures the held Instant and countdowns, checks hold/off/on/cancel/manual Next, renders the numeric row, Instant and active Next Up in all five locales, and records decoded media and provider file request counts. The first fake episode serves the existing H.264/AAC clip to isolate sequencing from EAC3 compatibility. File requests include probes/ranges and are not logical session counts. Exact timing, single-open ordering, obsolete reads, receiver commands and an offline copy's independence from the viewing record are public-controller cases in `renderer/next-episode.test.ts` and `renderer/receiver.test.ts`; a downloaded episode going on to the next episode's copy, with the same delay, hold, Cancel and autoplay rules, is in `renderer/copy-next.test.ts` and the [Downloads entry](../downloads.md); persistence and older-reader round trips are in `preferences.test.ts`. This scenario does not establish native installed, audible-output or receiver-hardware acceptance.
