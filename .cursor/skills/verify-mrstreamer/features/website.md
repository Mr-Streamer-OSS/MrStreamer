# Marketing website

## Sub-features

Home with its finite motion, the desktop and iPhone stage, five tricks, the screen tabs and its questions, the download page with the visitor's system first, seven user guides, the grouped FAQ, release history, About, Security and Privacy, every page but Home answer first with its detail in collapsed sections, and website analytics with its footer and policy switch. Responsive layout and route/metadata correctness are part of the website contract.

## How to get to it (user POV)

Open Home. One header holds the mark, **Guides**, **FAQ**, **Discord** and **Download**. **Guides** opens `/docs`; select **Subscriptions** or another guide. **FAQ** in the header or footer opens `/faq`, with four groups of questions, each with its short answer on its line; clicking a question opens the full answer. Every non-home page opens answer first: its title and short answer, key points side by side on a guide, then each section collapsed with its one-line answer beside the heading on wide screens. A click, Enter or Space opens a section, also with scripts off, and a link to a section or anything in it opens it. A guide ends with the previous and next guide, only the next on a phone; `/docs` lists nine most asked tasks, then the seven guides. The old `/#questions` destination no longer exists; `/#downloads` is **Free. That's the whole trick.**: Mac, Windows and Linux, each with its requirement and its install routes as plain words (DMG; Microsoft Store and Setup .exe; AppImage and .deb), plus the build-written **Homebrew tap** and **AUR** links only while each package is published, an iPhone row reading Coming to the App Store with **Hear first on Discord**, then one Download button. Header Guides, FAQ, Discord and Download remain visible on phones. The header and footer each have a white Discord icon and label linking to the community invite, including on guides and 404 pages. Every **Download** on Home, in the header, the hero and the download section, opens `/download`: the visitor's own system first when the head script named it (Mac, Windows or Linux on a computer; nothing for a phone, an unknown system or scripts off), headed "Download for Mac" (or Windows or Linux), then a row for each other system with the Store, all four installers and the published package links, then the collapsed fine print: the Windows warning, checksums, Homebrew and AUR, source and older versions. Without a named system the heading is "Download", a line says to open the page on a computer, and every system's row shows. The version is on `/download`, not on Home. The hero has the big line, the h1, **Download** and **Read the source**. Below it the stage shows the desktop Home window with the iPhone Home screen in front. **Five tricks** (`#tricks`), names without links, lights the row nearest the middle of the screen while scrolling and, from 1120px, deals that trick's window cut beside it. **Same guide on the desk and on the couch.** (`#screens`) has tabs for TV Guide, Live TV, Movies and series and Watching, each a desktop window with the iPhone screen; arrow keys move between tabs, and the heading's noun follows the tab (guide, channels, library, show), reading "Same app" with scripts off. **Is it for you?** (`#what-you-need`) follows: a table with row headers for each need, Mr. Streamer's answer and the players documented to do it, stacked as rows under 700px below one line naming **Mr. Streamer** in white and **Also documented by** in grey, the colors of each row's two answers, and a dated **Sources** link to the README's comparison. FAQ's Getting started links to it from **How does it compare with other players?**. **Questions** (`#faq`) holds five open/close answers, the first open, matching the head's FAQPage data. Each section rises once as it scrolls in. With reduced motion nothing moves; with scripts off every trick is lit and every screen shows, without tabs. Footer links open **Releases**, **Privacy**, **About** and **Security**. Unknown addresses show a 404.

## Website analytics

Every page's footer reads **Site analytics: on.** with **Turn off** and **What's counted**; `/privacy#website-analytics` has the same switch. Events use PostHog's cookieless protocol and Web analytics names (`$pageview`, `$pageleave`, `$web_vitals`, `download_clicked` and the rest). `$pageleave` carries posthog-js's scroll-depth shares and `$web_vitals` one numeric LCP, INP or CLS from the pinned web-vitals, the properties PostHog's scroll-depth and web vitals health checks look for. `$pageview` and `download_clicked` also carry `entry_source`, `entry_medium` and `entry_campaign`, fixed codes from `apps/marketing/src/referrals.ts` for where the tab's visit entered, kept in session storage under `mrstreamer.site-entry`. Global Privacy Control or Do Not Track shows the off reason with no button, blocked storage shows off with no button, and a build without capture shows static "Site analytics: off." The events, properties and build variables are in `apps/marketing/README.md#website-analytics`; `docs/privacy.md` must match them.

Build with the EU host and a verification key, then run the scenario on headless Linux:

```sh
MR_STREAMER_SITE_ANALYTICS_RELEASE_BUILD=1 MR_STREAMER_SITE_ANALYTICS_HOST=https://eu.i.posthog.com MR_STREAMER_SITE_ANALYTICS_PROJECT_TOKEN=phc_mrstreamer_verification pnpm build:marketing
xvfb-run -a node .cursor/skills/verify-mrstreamer/scripts/website-analytics.ts
```

It serves that production-configured build, whose pages send to the site's own `https://mrstreamer.app/ingest/i/v0/e/`, and points its isolated browser's https through a loopback proxy that answers only `mrstreamer.app`, with a certificate the run makes and only that browser trusts, so no request reaches Vercel or PostHog. It requires the script to name no `i.posthog.com` host, resolves every capture through the packaged `.vercel/output/config.json` routes and requires each to reach `https://eu.i.posthog.com/i/v0/e/`, and records that GET, OPTIONS and other `/ingest` paths stay on the site. Outside links are clicked but not followed. It drives a fresh profile from Home with a private query and fragment, wheel scrolling and a footer GitHub click, then follows the hero's Download link to `/download` and clicks an installer there, requiring `download_clicked` with route `/download` and location `page`; opens Home from a tagged GitHub link whose CDP-set referrer is a whole private address, requiring `github`/`readme`/`release` and session storage holding only those codes, then keeps them through the header Downloads link, an installer click and a typed `/faq`, and requires `google`/`search`/`none` from a Google search and `other`/`referral`/`none` from an unlisted site with an unlisted tag; on `/docs/movies-and-series` adds a 200ms pointer handler, clicks the heading, inserts a 240px block and wheels part way down, requiring a CLS above 0, an INP of at least 150ms, an LCP and the scroll shares the page's own geometry gives; holds a guide's requests and turns off from the footer, requiring each held request to be cancelled and session storage empty; restarts on the same profile; turns on and requires nothing until the next page, which enters as `unknown`; opens `/faq#free`, then the policy's collapsed Information we collect section with the pointer and its switch at 390px and 1280px; clicks the header Guides link; holds a guide's requests past the 10-second deadline, requiring each to end; scrolls `/releases` and opens an unknown address with a private query and fragment, which must answer 404 and count as `/404`; then GPC, DNT and blocked storage, each after a page from Bing kept an entry, which the refused page must remove. A page turned off, opened off or refused must send nothing at all, its leave and vitals included. The 64-request cap is covered by the unit contracts. Every captured body is checked against the allowlist: distinct id `$posthog_cookieless` with `$cookieless_mode: true`, `$lib_custom_api_host` `https://mrstreamer.app/ingest`, `$current_url`/`$pathname`/`$host` built from `https://mrstreamer.app` and a fixed route, `$raw_user_agent` equal to that request's own `User-Agent` header, entry codes only on page views and download clicks, none of the private query, tag, click id or referrer words, and no Referer, cookie, preflight, query, fragment, `$session_id` or `$window_id`. Scroll shares must be 0 to 1 in hundredths with `$prev_pageview_pathname` equal to `$pathname`, and each `$web_vitals` exactly one finite vital: LCP and INP whole milliseconds under 15 minutes, CLS in thousandths. The `/releases` leave read to its foot must say 1. Proof, screenshots and the event list stay in `.local/verification/website-analytics-<unique>/`; the key is never written there. A `$pageleave` and `$web_vitals` from the page before a refusal are expected; the page holds no id, so they are matched to its earlier page view by `$pathname`. A page clicked, scrolled or left before its largest paint is recorded has no LCP, as web-vitals intends; the helper's quick first inputs can do that on Home and other pages, so it requires LCP only on the guide it waits on. T3's Chrome preview reported Home's after a first click. A page left by its only, navigating click may have no INP: none is made up. Chromium completes a keepalive leave or link-click request already sent. Real sites usually send only their origin and some send no referrer; the run's whole-address referrers test the stronger case, not real sites' policies. Unit contracts, including the registry's boundaries, malformed and repeated tags and failing session storage, are in `apps/marketing/test/analytics.test.ts`. PostHog ingestion, its cookieless hash and sessions, dashboards and the project's cookieless and IP settings are outside this proof; do not run it with a real key. So are Vercel's own forwarding of the route, including the visitor's IP address as `x-forwarded-for`, and PostHog's reverse proxy health check: both need the published site, read back after publication. The reviewer's frozen-tab off/on sequence is in `apps/marketing/test/analytics.test.ts` as a late storage event.

## IndexNow deployment notifications

Vite generates the canonical sitemap, UTF-8 root ownership file and unique `indexnow-build.json` from `PAGES`. `package-vercel.ts` validates their contents against the registry and source commit. The IndexNow job of `.github/workflows/website.yml` consumes artifacts from the same run without owner secrets, after an actual non-superseded website publication. It checks the literal public domain's ownership file and exact build marker before one bounded POST. Rollback pinning and propagation failures report failure with the deployment already complete. HTTP 200 means received; 202 means received with ownership validation pending. Neither proves indexing.

Run `pnpm vitest run apps/marketing/test/indexnow.test.ts` and `pnpm actionlint`, then `pnpm build:marketing`. Inspect the actual packaged ownership file, marker/revision, sitemap and Vercel filesystem routes. Retain local fixture request counts, outcomes and original exits. Tests use loopback public/API fixtures only. Do not submit to IndexNow during verification. Actual production propagation, search-engine receipt and indexing require separately authorized deployment and observed results. See `apps/marketing/README.md` for stable public-key rotation and bounded failure behavior.

For route or indexing changes, read the built `apps/marketing/.vercel/output/config.json`: each `PAGES` route is `caseSensitive` and takes an optional trailing slash. Against the owned preview, every sitemap address and its trailing-slash form answer 200 with the canonical link and `og:url` of the address without a slash or query and no robots `noindex`; `/DOCS`, `/index.html` and an unknown address answer the `noindex` 404 page. Read-only requests to the public domain may compare statuses, redirects and canonicals; Vercel's case handling there changes only after publication. Search Console URL examples and Google's indexing outcomes are account-only and belong on their own evidence card.
