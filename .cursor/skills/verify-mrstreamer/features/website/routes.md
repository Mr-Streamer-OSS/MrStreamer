# Website routes and browser baseline

## Sub-features

Home with its finite motion, the desktop and iPhone stage, five tricks, the screen tabs and its questions, the download page with the visitor's system first, seven user guides, the grouped FAQ, release history, About, Security and Privacy, every page but Home answer first with its detail in collapsed sections, and website analytics with its footer and policy switch. Responsive layout and route/metadata correctness are part of the website contract.

## How to get to it (user POV)

Open Home. One header holds the mark, **Guides**, **FAQ**, **Discord** and **Download**. **Guides** opens `/docs`; select **Subscriptions** or another guide. **FAQ** in the header or footer opens `/faq`, with four groups of questions, each with its short answer on its line; clicking a question opens the full answer. Every non-home page opens answer first: its title and short answer, key points side by side on a guide, then each section collapsed with its one-line answer beside the heading on wide screens. A click, Enter or Space opens a section, also with scripts off, and a link to a section or anything in it opens it. A guide ends with the previous and next guide, only the next on a phone; `/docs` lists nine most asked tasks, then the seven guides. The old `/#questions` destination no longer exists; `/#downloads` is **Free. That's the whole trick.**: Mac, Windows and Linux, each with its requirement and its install routes as plain words (DMG; Microsoft Store and Setup .exe; AppImage and .deb), plus the build-written **Homebrew tap** and **AUR** links only while each package is published, an iPhone row reading Coming to the App Store with **Hear first on Discord**, then one Download button. Header Guides, FAQ, Discord and Download remain visible on phones. The header and footer each have a white Discord icon and label linking to the community invite, including on guides and 404 pages. Every **Download** on Home, in the header, the hero and the download section, opens `/download`: the visitor's own system first when the head script named it (Mac, Windows or Linux on a computer; nothing for a phone, an unknown system or scripts off), headed "Download for Mac" (or Windows or Linux), then a row for each other system with the Store, all four installers and the published package links, then the collapsed fine print: the Windows warning, checksums, Homebrew and AUR, source and older versions. Without a named system the heading is "Download", a line says to open the page on a computer, and every system's row shows. The version is on `/download`, not on Home. The hero has the big line, the h1, **Download** and **Read the source**. Below it the stage shows the desktop Home window with the iPhone Home screen in front. **Five tricks** (`#tricks`), names without links, lights the row nearest the middle of the screen while scrolling and, from 1120px, deals that trick's window cut beside it. **Same guide on the desk and on the couch.** (`#screens`) has tabs for TV Guide, Live TV, Movies and series and Watching, each a desktop window with the iPhone screen; arrow keys move between tabs, and the heading's noun follows the tab (guide, channels, library, show), reading "Same app" with scripts off. **Is it for you?** (`#what-you-need`) follows: a table with row headers for each need, Mr. Streamer's answer and the players documented to do it, stacked as rows under 700px below one line naming **Mr. Streamer** in white and **Also documented by** in grey, the colors of each row's two answers, and a dated **Sources** link to the README's comparison. FAQ's Getting started links to it from **How does it compare with other players?**. **Questions** (`#faq`) holds five open/close answers, the first open, matching the head's FAQPage data. Each section rises once as it scrolls in. With reduced motion nothing moves; with scripts off every trick is lit and every screen shows, without tabs. Footer links open **Releases**, **Privacy**, **About** and **Security**. Unknown addresses show a 404.

## Driving it with browser/CDP

Preconditions: `pnpm install --frozen-lockfile`, then `pnpm build:marketing`. Build assets and route/link checks are local output only. The build may read public GitHub release metadata and installer headers; it does not deploy the site or download installers.

For interactive verification, use T3 collaborative preview first. Run the repo's `pnpm preview:marketing` with an unused loopback port and `--strictPort`, open that owned local URL, inspect a snapshot and click its semantic link handles. Capture Home, the changed route and the relevant narrow viewport. Verify actual link destinations, canonical/title metadata and status codes alongside the rendered page. Stop only the server you started. Do not attach to or deploy the production website.

When collaborative preview is absent or reports browser setup unavailable, run `pnpm verify:website`, or `xvfb-run -a pnpm verify:website` on headless Linux. This complete baseline session owns a Vite preview, isolated Electron browser and profile. It records real pointer navigation from Home through FAQ, the Downloads guide, Guides, Subscriptions, Downloads, Releases and Privacy, paired screenshots/accessibility trees and route metadata. It opens FAQ's Can I download? question with the pointer before following the Downloads guide link inside it. It also disables page scripts and repeats that, so a collapsed question opens and its link works without scripts. A link inside a closed section has a box in Chromium; the helper counts a link only when `checkVisibility()` holds. Keep the full navigation flow at 390px without horizontal overflow. Require known routes to answer 200 and an unknown route to answer 404. Check all four displayed installer destinations or their GitHub Releases fallback and the Microsoft Store product; the helper inspects links without following them. Its live doctor checks browser and server identity before driving and after each navigation. The helper captures after navigation or scrolling; an unchanged viewport reuses its preceding capture, named in the before-click proof. Captures wait for fonts, finite animations and rendering to settle; visually inspect them before accepting the proof. All proof remains in `.local/verification/website-<unique>/` after both processes and scratch state are removed.

The existing `apps/marketing/test/` suites verify OS detection, the home and download pages under their stylesheet, link/feed fallback, page rendering and release-history contracts. Run those for changes to those behaviors. For motion changes, prove on the built site that a section's `revealed` class and `will-change` go once its rise has finished, that `document.getAnimations().length` is 0 at idle after the opening and after each reveal, that the tricks' scroll listener is attached only while the tricks are on screen, and that with reduced motion the trick cards don't slide and with scripts off every trick is lit and every screen shows; record how it was observed. For Is it for you?, Questions or the download section changes, capture the section at 1440px or 1280px and 390px after its reveal settles, confirm no horizontal overflow and that it reads with scripts disabled. For the download section, always check `/download`. Check the Homebrew tap and AUR destinations independently when their verified routes are published; require each unpublished or withdrawn route to be absent. Confirm the system names share one aligned column on phones. For FAQ/privacy changes, capture the changed pages at desktop and 390px, open the questions, follow the FAQ links into the mapped-playlist, offline-download, update and privacy guides, and check their fragments. For document page layout changes, compare with the Answer first artboards (top row of the Paper page "Subpages · Round 1"), open a section and a question at both widths, open a link to a section's fragment and to a `###` inside one, and confirm the target section opens. With scripts disabled, a fragment on a section's heading lands on that closed heading, which opens with a click; Chromium opens a closed section by itself for a fragment inside it, such as a `###`, and browsers without that land on nothing visible until the section is opened. Markdown guides keep their lede, bold-led key points and italic section lines readable on GitHub; `apps/marketing/README.md` lists the rules. Check the header and footer on Home, generated pages and 404, keyboard focus, the retained `/#downloads` destination and readable FAQ content with scripts disabled. The policy follows collection, use, recipients and choices; keep its statistics and download claims aligned with delivered app behaviour.

The baseline alone does not exercise Windows/Mac user-agent variants, all seven guides, About/Security, live feed refresh, no-script mode or Safari. Use the installed `mac-mini` skill's control tools for native Safari checks on the Mac mini, recording the real browser and viewport.
